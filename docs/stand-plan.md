## Фаза 0. Контурный префикс (фундамент, всё остальное на нём)

Сейчас префиксы захардкожены в четырёх местах:

- `tests/live/conftest.py:170` — `live-test-{hex}`
- `tests/live/pipeline_helpers.py:349,364` — `live-test`, `live-test-llm`
- `tests/live/test_api_crud.py:17` — `live-crud-{hex}`
- `scripts/clean_live_tests.py` — `PROJECT_PREFIXES = ["live-test", "live-crud", "mega-test"]`

**Задача:** один источник правды — переменная окружения контура, например
`LIVE_CONTOUR_PREFIX` (default `live`, на стенде `stand`). Все имена собираются как
`f"{prefix}-test"`, `f"{prefix}-crud"`, `f"{prefix}-mega"`, и sweep берёт список оттуда же.

**Важная деталь truncation.** `generate_project_slug` режет заголовок до 40 символов вместе с UUID,
поэтому от префикса в имени стека остаётся 7 символов:

```
live-test        -> live-te-<uuid32>
mega-test        -> mega-te-<uuid32>
stand-live-test  -> stand-l-<uuid32>
stand-mega-test  -> stand-m-<uuid32>
```

`stand-l-` и `stand-m-` различимы — префиксы годятся. Но правило надо зафиксировать тестом:
**два контурных префикса обязаны различаться внутри первых 7 символов слага**, иначе sweep одного
контура увидит стеки другого. Это ровно тот баг, который снесёт прод-прогон.

**Definition of done фазы 0:**
- [ ] префикс приходит из env, дефолт сохраняет текущее прод-поведение байт-в-байт;
- [ ] `clean_live_tests.py` сметает только свой контур (тест на то, что `live-*` не попадает под `stand-*` и наоборот);
- [ ] тест на 7-символьную различимость префиксов;
- [ ] `GITHUB_ORG` в `clean_live_tests.py` перестаёт быть константой (берётся из env, дефолт прежний).

### Telegram: что нужно, а что нет

**PO-бот стенду не нужен.** Мега и матрица драйвят пайплайн через API
(`po_default_preflight.py` — PO-tool boundary по HTTP), сервис `telegram_bot` в прогоне не
участвует. Telethon же нужен для другого — он разговаривает с ботами **сгенерированных проектов**
(`test_bot_access_revocation.py`, QA ботов-приложений).

- [ ] на стенде **не поднимать** сервис `telegram_bot` (compose-override / `--scale telegram_bot=0`):
      он хардфейлит без токена (`services/telegram_bot/src/main.py:496`), а пустую переменную
      оставить нельзя. Уведомления это не ломает — `notify_admins_best_effort` best-effort;
- [ ] **прод-токен бота на стенд не класть никогда**: два long-polling клиента на одном токене
      воруют апдейты друг у друга, прод-PO начнёт терять сообщения;
- [ ] `TELETHON_API_ID`/`API_HASH` переиспользуем прод-овские: `my.telegram.org` выдаёт одну апку на
      аккаунт, но одна апка обслуживает сколько угодно сессий;
- [ ] `TELETHON_SESSION` — **новая строка**, выпущенная тем же `api_id`
      (`scripts/make_stand_session.py`). Делить одну сессию между контурами нельзя: два клиента с
      одним auth key дерутся, Telegram может отозвать авторизацию и уронить прод-QA;
- [ ] аккаунт под сессию стенда — пока тот же, что у прод-QA (общий `concurrency` group и так
      запрещает параллельные прогоны). Отдельный номер — когда стенд начнёт гоняться часто;
- [ ] отдельный PO-бот для стенда — **опционально, потом**, если захочется тыкать стенд руками из
      телеги. Для e2e не требуется.

`TIME4VPS_MANAGED_SERVER_IDS` на стенде — **пустой**: это штатный default-deny, стенд физически не
сможет тронуть прод-таргеты. `TIME4VPS_LOGIN/PASSWORD` не заводим вовсе (API всё равно закрыт
IP-allowlist'ом на прод-адрес).

## Фаза 2. Self-deploy: стенд как собственный таргет

Мега доводит проект до реального деплоя на managed-сервер. Без второй машины таргетом становится
сам стенд.

- [ ] завести на стенде отдельного пользователя под деплой приложений (`stand-deploy`), не `dev`;
- [ ] сгенерировать ключевую пару для infra-service, публичный ключ — этому пользователю,
      приватный — в БД стенда (ключи managed-серверов хранятся per-server в БД, монтировать в
      compose ничего не нужно);
- [ ] зарегистрировать сам стенд через `POST /api/servers/` и **явным PATCH перевести в
      `pending_setup`** — это не-деструктивный SSH-путь, без reinstall (см. `docs/DEPLOY.md`);
- [ ] проверить, что provisioner создаёт `/opt/services` с `root:stand-deploy`, mode `3770`;
- [ ] развести порты: у стенда уже занят 80/443 своим Caddy, целевые стеки должны получать порты
      из аллокатора; проверить, что аллокатор не выдаёт 80/443/5432/6379;
- [ ] ufw: наружу оставить 22/80/443, порты целевых стеков **не открывать** — доступ к ним только
      с самого хоста (e2e ходит с localhost).

Риск: рекурсия «оркестратор деплоит на хост, где живёт сам». Мера — отдельный пользователь,
отдельный каталог `/opt/services`, и запрет sweep'у трогать каталоги вне `/opt/services/stand-*`.

## Фаза 4. Цели запуска (Makefile, а не только кнопка)

Всё, что делает джоба, должно быть вызываемо по SSH:

- [ ] `make stand-up` — `.env` из Environment, `alembic upgrade head`, `seed_system_configs`,
      health-check, регистрация себя как таргета;
- [ ] `make stand-preflight` — подписки, доступ к GitHub App, свободное место, наличие worker-образов;
- [ ] `make stand-e2e` — мега; `make stand-e2e MATRIX=1` — матрица 2×2 claude/codex;
- [ ] `make stand-clean` — sweep своего контура;
- [ ] `make stand-reset` — быстрый откат БД к чистому снапшоту (см. фазу 5).

Из `agent-matrix.yml` вынести прод-специфику (пользователь `deploy`, `/opt/codegen_orchestrator`,
отдельный API-контейнер на `127.0.0.1:8000`, `make rebuild-worker-images` на каждом прогоне).
На 2 vCPU пересборка воркер-образов каждый раз — неприемлемо долго: стенд должен **тянуть образы по
digest**, как это делает деплой, и пересобирать только по явному флагу.

## Открытые риски

1. **Ресурсы.** 2 vCPU / 4 GB / 50 GB на ~20 сервисов + воркер-контейнеры + целевые стеки — впритык.
   Первое, что делаем после фазы 1: снимаем реальный футпринт и решаем, гасить ли на стенде
   grafana/loki/registry. Своп на 4 ГБ добавить сразу.
2. **Общая орга.** Пока префикс — единственная граница между стендом и продом. Любая правка sweep'а
   и матчеров требует теста на обе стороны. Это временная мера до отдельной орги.
3. **Одна подписка на два контура.** Параллельный прогон прод-матрицы и стенда — риск рейт-лимита.
   Лечится общим `concurrency` group (фаза 1).
4. **Общий GitHub App.** Стенд получает тот же приватный ключ, что прод. Отдельный App желателен
   сразу после отдельной орги.

## Порядок работ

Фаза 0 → 1 → 2 → 3 → 4 → 5 → 6. Фазы 0 и 1 — обязательный фундамент (без них стенд опасен для прода),
2–4 дают первый зелёный прогон меги на стенде, 5–6 делают его пригодным для регулярного использования.
