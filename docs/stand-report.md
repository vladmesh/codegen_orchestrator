## Инфраструктурные проблемы: найдены и починены

Все шесть вмержены в main (#318–#323).

1. **Секреты репозитория наследуются в Environment.** Стенд молча получил прод-овский
   `PROVISIONING_POLICY_TIME4VPS_MANAGED_SERVER_IDS` — то есть право переустанавливать прод-серверы. Первый деплой
   упал на собственном предохранителе. Теперь workflow пишет эти значения пустыми вне прода, а
   проверка читает записанный `.env`. (#320)
2. **Окно healthcheck у `api` — ~25 секунд.** На 2 vCPU при старте двадцати контейнеров не
   укладывается; API отвечал 200 минутой позже, когда деплой уже сдался. Оверлей стенда сохраняет
   прод-овскую проверку и увеличивает терпение. (#321)
3. **bcrypt-хэши в `.env` требуют удвоенных долларов** — иначе docker compose съедает `$2y$05$`
   и registry отвечает 401. Мой хэш приезжал 41 символом вместо 60. Прод так и хранит: `$$2y$$05$$…`.
4. **Метка допуска.** `shared/server_admission.py` пускает сервер под аллокацию только с
   `labels.provisioning_phase=complete`, а пишет её провижинер, который на стенде намеренно не
   запускается. Регистрация теперь ставит её явно. (#322)
5. **Ёмкость, при которой арифметика не сходится никогда.** Допуск требует
   `capacity ≥ used + 768`; при used ≈ 1.8 ГБ моя «осторожная» ёмкость 2048 не пускала ничего.
   Поднято до 3400. Заодно сходящийся PATCH теперь переносит ёмкость — без этого повторный запуск
   скрипта молча откатывал ручные правки. (#323)
6. **Имена БД.** Харнесс ходит в базу жёстко как `-U postgres -d orchestrator`; я задал стенду
   свои имена, и очистка падала на «role postgres does not exist». Стенд приведён к ожидаемым
   именам, пароль остался уникальным.

Отдельно: `X-Internal-Key` вместо выдуманного мной `X-Internal-API-Key`, установка uv и
monitoring-baseline (node_exporter + cadvisor) — без него health-checker метит сервер
`unreachable`, и он тоже никогда не аллоцируется.

## Что оказалось не багом

В первой редакции я записал в баги кодгена две вещи. Обе исчезли, когда у стенда появился
отдельный целевой сервер `vps-275928` (`176.223.138.154`), и обе были следствием того, что
оркестратор и цель деплоя жили на одной машине.

### 1. Крешлуп приложения на резолве `db` — не код приложения

Симптом был стойкий: 74 падения `failed to resolve host 'db'`, 36 рестартов, при живых и здоровых
`db` и `redis` в той же сети. Я сначала объяснил это тем, что приложение не ретраит подключение —
объяснение неверное, и оно противоречило собственным данным: за полчаса хоть одна из 36 попыток
выиграла бы гонку.

Зонд в момент крешлупа показал настоящую причину: у контейнера в цикле рестартов
`resolv.conf` содержал **апстрим-DNS хоста** (`109.235.67.143`), а не встроенный резолвер Docker
`127.0.0.11`, и список привязанных сетей был пуст — при корректном `NetworkMode`. В состоянии
`created`, до первого запуска, резолвер был правильный. То есть контейнер терял привязку к сети и
оставался без резолвера навсегда; приложение не могло резолвить в принципе.

На отдельной машине это не воспроизводится: то же приложение, тот же шаблон, деплой прошёл, health
принят, мега зелёная. Причина была в том, что на одном docker-демоне жили оркестратор, его воркеры
и целевые стеки одновременно.

### 2. Очистка требовала Time4VPS `provider_id` — и была права

`cleanup_target_skip_reason` допускает к очистке только сервер с валидным провайдерским ID из
allowlist. У `stand-self` его быть не могло, потому что стенд деплоил сам в себя, а свой ID в
allowlist не значился. Отсюда «server list fetch returned no managed cleanup target» на каждом
прогоне, дошедшем до деплоя.

С отдельным таргетом это правило выполняется само: `vps-275928` в allowlist, `provider_id` есть,
очистка отработала — `/opt/services` на цели пуст, на стенде не осталось ни контейнеров, ни
проектов. Менять fail-closed правило не потребовалось.

**Вывод, который стоит запомнить:** совмещение оркестратора и цели деплоя на одной машине — не
экономия, а источник ложных багов. Полдня диагностики ушло на симптом, которого в продуктовом коде
не было.

## Что подтвердилось про изоляцию

Когда стенду выдали доступ к API провайдера и allowlist из одного ID:

- sync обнаружил **все** серверы аккаунта, но управляемым сделал только `275928`; прод-машины
  получили статус `reserved` и `is_managed=False`;
- `stand-self` автоматически вышел из-под управления по тому же правилу;
- провижининг чужой машины отработал целиком и впервые: переустановка ОС через API провайдера со
  своим ключом, плейбук доступа (7 минут), плейбук софта (11 минут), метка
  `provisioning_phase=complete` и `qa_ssh_user=qa-observer`.

Одна шероховатость: первая попытка провижининга упала, потому что за секунду до явного
`force-rebuild` стартовала джоба восстановления по инциденту `unreachable` и пошла
непереустановочным путём. Интент при этом сохранился, как и написано в контракте, но republish ждал
30-минутного окна `provisioning_stuck_timeout_seconds`. Снятие отметки `provisioning_started_at`
опубликовало джобу сразу. Кандидат на улучшение: явный admin-интент мог бы иметь приоритет над
восстановительной джобой, а не ждать общий stuck-таймаут.

## Операционное наблюдение

Деплой отказывается ставить ревизию без опубликованного релиза worker-образов (`exit 9`) — это
правильная защита, но publish идёт только на push в main. Поэтому после каждого мержа приходится
ждать publish и лишь потом деплоить; за ночь я упёрся в это трижды. Кандидат на автоматизацию:
деплой мог бы сам дожидаться релиза своей ревизии.
